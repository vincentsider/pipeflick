<objective>
A per-account run allowance, so an invited account cannot spend the operator's OpenAI credit
without limit.

Purpose: the invite list decided in 06-02 bounds WHO registers. It does not bound HOW MUCH an
invited account spends, and every run is a real charge on the operator's key — $0.097 measured
on production run 1. This is the other half of Vincent's reason for choosing the invite list.

Deliberately an allowance, not credits: no balance to top up, no payments, no ledger to
reconcile. The operator sets a number and it counts down. Phase 7 replaces it with paid
credits, and Task 2 puts the seam where that swap happens.

Output: migration 0010, an allowance check in front of run creation, and the remaining count
on screen.
</objective>

<task type="auto">
  <name>Task 1: Migration 0010 and the allowance helpers</name>
  <files>migrations/0010_allowance.sql, src/db.ts</files>
  <action>
    Create `account_allowance`: `owner_email` PRIMARY KEY, `runs_remaining` INTEGER NOT NULL,
    `updated_at` TEXT NOT NULL. One row per account.

    Backfill a row for vincent@getinference.com with a large number — the operator's own
    account should not be throttled by a feature that exists to throttle guests. Put the number
    in the migration, not in code, so changing it later is a D1 command and not a deploy.

    A MISSING ROW MEANS ZERO, NOT UNLIMITED. An account that has never been granted anything
    has no row, and the read must return 0 for it. Defaulting a missing row to unlimited would
    mean every newly invited account starts with an uncapped key — precisely the thing this
    plan exists to prevent, arriving silently.

    Add to `src/db.ts`, all owner-scoped:
      - `getAllowance(db, owner)` → number, 0 when there is no row
      - `grantRuns(db, owner, runs)` → upsert, for the operator
      - `spendRun(db, owner)` → boolean

    `spendRun` MUST be a single conditional UPDATE, not a read-then-write:
      `UPDATE account_allowance SET runs_remaining = runs_remaining - 1, updated_at = ?
       WHERE owner_email = ? AND runs_remaining > 0`
    and it returns `meta.changes === 1`. This is the same claim-then-work shape `claimNextJob`
    uses (03-02) and for the same reason: two tabs submitting at once would both pass a
    read-then-check and both start a run. The `runs_remaining > 0` in the WHERE clause is what
    makes the decrement atomic, and it also makes going negative structurally impossible.

    Apply to local AND remote (retry once past the known 7403 transient).
  </action>
  <verify>
    Run the exact SQL against seeded local D1: spend from an allowance of 1 returns changes=1
    and leaves 0; spending again returns changes=0 and leaves 0, never -1. An account with no
    row reads 0 and cannot spend. Paste the numbers into the SUMMARY.
  </verify>
  <done>Allowance can be granted, read and atomically spent, and cannot go negative.</done>
</task>

<task type="auto">
  <name>Task 2: Refuse a run with no allowance left</name>
  <files>src/runs.tsx</files>
  <action>
    In `POST /runs`, call `spendRun` BEFORE `createRun`. If it returns false, render a clear
    message — the account is out of runs and should ask the operator — and create nothing. No
    run row, no outliers, no drafts.

    Order matters and is the whole point: spend first, then create. Creating first and spending
    after would leave a run that was never paid for if the spend failed, and the run engine
    would happily pay OpenAI for it.

    PUT THE CHECK BEHIND ONE FUNCTION. Write it as a single `assertCanStartRun(db, owner)` used
    by the route, rather than inlining the `spendRun` call. Phase 7 replaces an allowance with a
    credit balance, and when it does, the body of that one function changes and the route does
    not. That seam is deliberate — name it in a comment so it survives.

    Do NOT refund on failure. A run that fails at step 3 has already spent real money on steps
    1 and 2, so returning the allowance unit would be the wrong direction. Say this in a comment:
    the unit buys an attempt, not a guaranteed result. The operator can grant more if a failure
    was the system's fault. (Phase 7's credits meter per step and can be fairer, because a
    credit is divisible where "a run" is not.)

    The engine itself — `POST /runs/:id/step` — is NOT gated. The allowance is spent at
    creation, and a half-finished run must be able to finish; stranding a paid-for run at step 4
    would waste the money already spent on steps 1 to 3.
  </action>
  <verify>
    Drive it through the live route: with allowance 1, the first POST /runs 303s to a real run
    and the second returns the out-of-runs page. Confirm with SQL that the refused attempt
    created ZERO rows in runs, outliers and drafts. Confirm a run created with the last unit can
    still be advanced to completion by the step route.
  </verify>
  <done>A run cannot start without allowance, a refused attempt writes nothing, and a started run can always finish.</done>
</task>
