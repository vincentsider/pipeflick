<task type="checkpoint:decision" gate="blocking">
  <decision>How open should registration be?</decision>
  <context>
    An Access policy decides who can get a one-time PIN, and Cloudflare only mails the PIN to
    addresses the policy allows — so the policy IS the registration gate.

    This matters beyond convenience. Every account that registers can spend the operator's
    OpenAI credit: a run costs about $0.10, measured on production run 1. An open policy is an
    open funnel to that spend, and it consumes the 50 free Zero Trust seats. Whichever shape
    is chosen, the rest of the phase is identical — only the dashboard rule differs.
  </context>
  <options>
    <option id="invite-list">
      <name>Explicit email list, operator edits it</name>
      <pros>No abuse surface at all. Zero code. The operator knows every account. Matches the pilot's "one or two people" scope.</pros>
      <cons>Registration is "email Vincent" — not self-service, so ACCT-01's "without manual allow-listing" is only half met.</cons>
    </option>
    <option id="email-domain">
      <name>One or more email domains</name>
      <pros>Genuinely self-service for anyone at those firms. Still bounded. No code.</pros>
      <cons>Only works if the pilot users share a domain; anyone at that domain can register.</cons>
    </option>
    <option id="open-plus-code">
      <name>Open one-time PIN, plus an in-app invite code on first sign-in</name>
      <pros>Fully self-service and satisfies ACCT-01 literally. The code is checked before any row is created, so an uninvited visitor owns nothing.</pros>
      <cons>Real code to write and test. Anyone can still occupy a free seat by authenticating, even if they never get past the code.</cons>
    </option>
  </options>
  <resume-signal>Select: invite-list, email-domain, or open-plus-code</resume-signal>
</task>

<task type="auto">
  <name>Task 1: Derive the owner from the Access identity</name>
  <files>src/access.ts, test/access.test.ts</files>
  <action>
    Keep `requireAccess` exactly as it is — fail-closed, no bypass switch. It already sets
    `email`. Add the normalisation that turns that email into the account key, and set it on
    the context as `owner` alongside `email`:

    - Lowercase and trim. Access returns whatever the user typed, and `Vincent@x.com` and
      `vincent@x.com` are the same inbox and must be the same account. Without this, one person
      can end up owning two disjoint sets of data and neither looks broken.
    - Export `OWNER_SYSTEM = ""` as the reserved system owner that migration 0008 uses for the
      health row. Assert in a test that no normalised identity can ever equal it: an Access
      identity is always a real address, and an empty or missing identity must NOT silently
      become the system owner — it must be treated as no access at all.
    - `AppEnv["Variables"]` gains `owner: string`.

    Do NOT change what happens when there is no Access context. That path still returns 403.

    If the decision was `open-plus-code`, this task ALSO adds the invite-code check: the code
    lives in a Worker secret, is checked before any row is created for a new owner, and a
    wrong code returns 403 with no row written. Do not build this if another option was chosen.
  </action>
  <verify>
    `npm test` passes, including new tests that: a mixed-case address normalises to one owner;
    a blank or missing identity does not produce OWNER_SYSTEM; `npm run check` exits 0.
  </verify>
  <done>`c.get("owner")` is available to every route and is a normalised address, never "".</done>
</task>
