<feature>
  <name>Credential sealing</name>
  <files>src/credentials.ts, test/credentials.test.ts</files>
  <behavior>
    `sealCredential(masterKeyBase64, plaintext)` → a text record safe to store in D1.
    `openCredential(masterKeyBase64, record)` → the original plaintext.

    Cases to write as tests BEFORE the implementation:
      - Round trip: `open(seal(k, "sk_abc"))` is `"sk_abc"`.
      - Non-determinism: sealing the same value twice gives two different records. AES-GCM
        with a reused IV is broken, so a fresh random 12-byte IV per record is the property
        being pinned, not an implementation detail.
      - No plaintext: the sealed record does not contain the plaintext as a substring.
      - Tamper: flipping a byte of the ciphertext makes `open` throw or return null. It must
        NEVER return different plaintext — that is what the GCM auth tag is for, and a caller
        that silently got the wrong key would send it to Fireflies.
      - Wrong master key: opening with a different key fails the same way.
      - Empty IV is rejected by Workers, so a record with a zero-length IV must be refused
        rather than passed to crypto.subtle.
      - Unicode survives a round trip (a key is ASCII, but the function must not quietly
        corrupt anything).
      - Malformed input: a record that is not the expected shape returns null rather than
        throwing an unhandled error, matching how `parseGrounding` treats unreadable JSON.

    The record carries a version marker (`CREDENTIAL_KEY_VERSION`) so a later master-key
    rotation can tell sealed-with-what without guessing. Rotation itself is out of scope.
  </behavior>
  <implementation>
    WebCrypto only — `crypto.subtle.importKey` with AES-GCM, `encrypt`/`decrypt`, and
    `crypto.getRandomValues` for the IV. Workers supports AES-GCM fully (DISCOVERY.md Q2).
    No npm dependency. Base64 for both IV and ciphertext so the record is one TEXT column.

    Keep this module pure and import-free, the same discipline `src/prompts.ts` holds: it
    takes the master key as an argument and must never read `c.env` itself. A module that
    reaches for the environment cannot be tested and invites the key into a log line.

    The docstring must state the limit plainly: the master key is a Worker secret, so anyone
    who can deploy the Worker can open every credential. This defends against a D1 dump, not
    against a compromised Cloudflare account. Claiming more than that would be false.
  </implementation>
</feature>
