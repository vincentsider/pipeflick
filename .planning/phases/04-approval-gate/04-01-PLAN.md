<task type="auto">
  <name>Task 1: Migration 0005 — decision, final text and timestamp on drafts</name>
  <files>migrations/0005_decisions.sql</files>
  <action>
Add exactly three nullable columns to `drafts`, one `ADD COLUMN` per `ALTER TABLE`
(SQLite/D1 takes no more), none `NOT NULL` because rows already exist in both
databases:

- `decision TEXT` — 'accepted' | 'edited' | 'rejected'. NULL means undecided, and
  that is a real state, not a defect: every draft written before this migration,
  and every draft in a run the executive has not reviewed yet.
- `final_body TEXT` — the post as it stands after the decision. Set on 'accepted'
  (a copy of `body`) and on 'edited' (the executive's text). NULL on 'rejected'
  and while undecided. Written on accept even when nothing changed, so "final
  text" is a column and not a COALESCE the reader has to remember.
- `decided_at TEXT` — ISO timestamp of the decision.

`body` is never overwritten by any of this. It is the model's original output and
it is one half of the measurement; an edit that destroyed it would make the
light-edit rate uncomputable from that row forever.

Write the header comment in the style of 0003 and 0004 — what the columns are for
and what NULL means — and include the actual one-query APPR-05 measurement in it,
so the claim "computable with one query" is checkable rather than asserted:

```sql
-- APPR-05, the whole measurement, one query:
--   SELECT decision,
--          COUNT(*) AS n,
--          AVG(ABS(length(final_body) - length(body))) AS avg_char_delta
--   FROM drafts WHERE decision IS NOT NULL GROUP BY decision;
-- `avg_char_delta` is a PROXY for edit size, not an edit distance. It says how
-- much text moved, never how much meaning did. Report it as what it is.
```

Nothing here changes what leaves the Worker; the compliance note at the head of
0003_runs.sql still governs.

Then apply it to BOTH databases:
- `npm run db:migrate:local`
- `npm run db:migrate:remote` — if this returns Cloudflare API error 7403, retry
  once before re-authenticating (03-02 hit it on a valid token and it succeeded
  immediately on retry; 03-06 did not hit it at all).

Remote schema will be ahead of remote code until 04-03 deploys. That is safe and
deliberate: all three columns are nullable and no deployed code reads or writes
them. It is the same order 03-06 and 03-07 used.
  </action>
  <verify>
- `npx wrangler d1 execute pipeflick-db --local --command "PRAGMA table_info(drafts)"` lists decision, final_body and decided_at
- The same command with `--remote` lists them too

  </verify>

<task type="auto">
  <name>Task 2: Decision write, approved-post read, and decisions in the run views</name>
  <files>src/db.ts</files>
  <action>
Four changes, all following the existing conventions in this file: bound
parameters everywhere, no `RETURNING`, no draft or transcript bodies in any list
projection, and **no import from src/prompts.ts** — that boundary is the
Jersey/JFSC guarantee and a caller-computed primitive is always the right answer
here (see `createRun`'s coverage parameter and `finishDraft`'s structural
`GroundingRecord`).

1. `export type Decision = "accepted" | "edited" | "rejected";` with a comment
   that NULL is undecided, and that 'edited' is *derived by comparison* rather
   than self-reported — the route decides it, not the user (04-02 owns that).

2. `DraftView` gains `decision: Decision | null`, `final_body: string | null` and
   `decided_at: string | null`, and `getRunView`'s drafts projection selects all
   three. The run page needs the decision to render it and `final_body` to
   prefill the edit box.

3. `export async function recordDecision(db, runId, draftId, decision, finalBody):
   Promise<boolean>`:
   - `UPDATE drafts SET decision = ?1, final_body = ?2, decided_at = ?3,
     updated_at = ?3 WHERE id = ?4 AND run_id = ?5`
   - Scoped by `run_id` as well as `id` on purpose: the draft id arrives in a URL
     under a run, and a draft belonging to another run must not be reachable
     through it. Do not check ownership with a separate SELECT — one guarded
     UPDATE is both the check and the write.
   - Returns `result.meta.changes === 1`, the same way `claimNextJob`'s claim
     decides its winner. False means "no such draft in this run"; the caller
     turns that into a 404.
   - `finalBody` is `string | null`; pass NULL for 'rejected'.

4. Decisions in the run list (APPR-06). `RunSummary` gains
   `decisions: DraftDecision[]`, where
   `export type DraftDecision = { position: number; decision: Decision | null; status: JobStatus }`.
   Implement it as a SECOND query inside `listRuns`, not as more correlated
   subqueries and not as a per-run read:
   `SELECT run_id, position, decision, status FROM drafts ORDER BY run_id, position`
   then group in JS onto the summaries. Two queries total for the whole page,
   no N+1, no bodies. (`listRuns` already counts jobs with subqueries and STATE
   already records that it would want a limit if the history grew; this adds one
   flat query rather than four more subqueries per row.)

5. `export async function listApprovedPosts(db, limit, excludeRunId): Promise<string[]>`:
   - `SELECT final_body FROM drafts WHERE decision IN ('accepted','edited')
     AND final_body IS NOT NULL AND run_id != ?1 ORDER BY decided_at DESC LIMIT ?2`
   - Returns the bodies newest first. `limit` is passed in by the caller, which
     reads `MAX_APPROVED_POSTS` from src/prompts.ts — this module must not import
     that constant.
   - `excludeRunId` is not defensive padding. It keeps a run's own drafts out of
     its own prompt, which stops draft 3 echoing draft 1 after a mid-run
     approval, and keeps the cacheable prompt prefix byte-stable across the three
     drafting calls of a single run.
  </action>
