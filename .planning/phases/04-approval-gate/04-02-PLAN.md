<task type="auto">
  <name>Task 1: Decision controls under each draft, and the route that records them</name>
  <files>src/runs.tsx</files>
  <action>
**The form.** Extend `DraftSection` so a draft that has a body renders, below its
post and below `GroundingPanel`, one form per draft:

```
<form method="post" action={`/runs/${runId}/drafts/${draft.id}/decision`}>
  <textarea name="body" rows="8">{draft.final_body ?? draft.body}</textarea>
  <button type="submit" name="decision" value="accept">Accept</button>
  <button type="submit" name="decision" value="reject">Reject</button>
</form>
```

Two submit buttons sharing a name is plain HTML and needs no client JavaScript,
which is the rule everywhere in this app. `DraftSection` now needs `runId`, so
pass it from the route.

**Accepted vs edited is measured, not declared.** There is no third button. The
route compares the submitted text against the stored `body` and writes 'accepted'
when they match, 'edited' when they do not. A self-reported "I only tweaked it"
would make APPR-05 a survey; a comparison makes it data. Say so in a comment —
this is the same instinct as 03-05's calibration and 03-06's stored counts.

**Newline normalisation is load-bearing.** Browsers submit textarea content with
CRLF line endings (HTML spec), and every draft in D1 has LF. Without normalising
first, *every* accept would be recorded as an edit and the light-edit rate would
read 0% forever. Add a small local helper:

```
/** Textareas come back CRLF-normalised per the HTML spec; D1 holds LF. */
function normalisePost(text: string): string {
  return text.replace(/\r\n?/g, "\n").trim();
}
```

Compare `normalisePost(submitted)` against `normalisePost(draft.body)` and store
the normalised value.

**Show the decision.** Above the form, render the current state: nothing yet, or
"Accepted", "Accepted with edits" or "Rejected" plus the date from `decided_at`
(`formatDateTime`, already in this file). Use `.notice` for accepted, `.notice
.warn` for rejected — matching 03-03's rule that amber is a reviewer's cue and
red is reserved for a failed step. A rejected draft still shows its post; the
decision is a record, not a delete.

**When the controls appear.** Render them only when the page is not
auto-advancing (`!advance.auto`), i.e. once the run has finished or halted. The
status page submits itself every 400ms while work is claimable (03-04's engine),
and a page that reloads under a half-typed edit would throw the edit away. When
they are hidden, render one hint: "Decisions open when the run stops generating."
Pass this in as a single `interactive` prop rather than re-deriving it inside the
component.

**The route.** `runs.post("/runs/:id/drafts/:draftId/decision", ...)`:
- `RUN_ID_PATTERN` on the run id as every other route does; `/^\d{1,9}$/` on the
  draft id. Either failing is a plain-text 400, matching the precedent in this
  file and in `src/sources.tsx`.
- `field(form["decision"])` must be exactly "accept" or "reject"; anything else
  is a 400. Never infer a decision from a missing value.
- On "reject": `recordDecision(db, runId, draftId, "rejected", null)`.
- On "accept": read the textarea. Empty after normalising is a 400 ("A post
  cannot be empty"). Longer than `MAX_DECISION_BODY_CHARS` (define it as 5000 —
  LinkedIn's own ceiling is 3000, so this is headroom, not a novel) is a 400.
  Then `getRunView` to read the draft's stored `body`, compare, and
  `recordDecision(db, runId, draftId, same ? "accepted" : "edited", normalised)`.
- `recordDecision` returning false means the draft is not in this run: 404 "Draft
  not found". That is the whole ownership check — one guarded UPDATE, no separate
  SELECT for permission.
- Finish with `c.redirect(`/runs/${runId}`, 303)`, the POST-then-redirect pattern
  used by every form in this app, so a reload never re-posts.

Do not touch the step route, `planAdvance`, `RunControl`'s auto-advance script or
`GroundingPanel`. Two things in `RunControl` do need a word: the finished-run
notice still says "Accepting, editing and rejecting them is Phase 4, so for now
this page is read-only" — rewrite it now that it is not. And the bare `grounded`
boolean stays unrendered; 03-07 retired it deliberately and the approval gate is
exactly where a known-false signal would do the most damage.
  </action>
  <verify>
- `npm run check` exits 0 and `npm test` still passes
- Against `npm run dev` with a seeded local run whose drafts are 'done':
  1. Accept a draft without touching the text → the page shows "Accepted"; D1 has `decision='accepted'`, `final_body` equal to `body`, `decided_at` set
  2. Change one word and Accept → "Accepted with edits"; D1 has `decision='edited'`, `final_body` holding the new text, and `body` UNCHANGED
  3. Reject a draft → "Rejected"; `final_body` is NULL and the post still renders
  4. Refresh each time → the decision is still there
  5. Accept a draft that was rejected → the decision changes
  6. POST a draft id belonging to a different run → 404, and that draft is unchanged in D1
  7. POST with an empty textarea → 400, nothing written
  8. A run still mid-generation shows no controls, only the hint
- Delete every seeded row and confirm local D1 is back to zero
  </verify>
