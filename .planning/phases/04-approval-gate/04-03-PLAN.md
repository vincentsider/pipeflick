<task type="auto">
  <name>Task 1: The approved_posts block, its instructions, and the tests that pin them</name>
  <files>src/prompts.ts, test/prompts.test.ts</files>
  <action>
`src/prompts.ts` is this project's compliance boundary. It has **zero imports**
and takes **primitives only**, and both halves are asserted by test. Nothing here
may weaken either.

**Constants**, named, beside `MAX_SAMPLES` — never inline at the call site, per
03-01's rule that every cap in this file is a named constant:
- `MAX_APPROVED_POSTS = 3`
- `MAX_APPROVED_CHARS = 2500` (the voice-sample cap; an approved post is the same
  kind of object and the same size)

**`buildDraftingInput` gains `approvedPosts: string[]` as its SECOND parameter**,
so the argument order matches the block order the doc comment has promised since
03-01 ("Phase 4 inserts <approved_posts> directly after </voice_samples>, still
inside the cacheable prefix"). New signature:

```
buildDraftingInput(samples: string[], approvedPosts: string[], transcriptBody: string, template: Template)
```

The block renders between `</voice_samples>` and `<transcript>`, capped and
joined with `\n---\n` exactly as the samples block is, and **renders even when
empty** — the same rule and the same reason: a stable prefix shape is what makes
drafts 2 and 3 of a run cache-eligible.

**`DRAFT_INSTRUCTIONS`.** The numbered list becomes four items, with APPROVED
POSTS as item 2, and two new rules. Keep every existing pinned phrase verbatim —
the banned-word list, "Invent nothing.", the do-not-name-clients rule, the
never-mention-a-transcript rule and the em-dash ban are all asserted by test and
a reword would silently drop one.

- Item 2: `APPROVED POSTS - posts this system drafted that the executive
  approved, some of them after editing. They show the voice and the standard that
  gets accepted.`
- A grounding rule, because this is the line that keeps the new block honest:
  `- APPROVED POSTS are not a source of facts. Take voice from them; never take a
  claim, number, example or story from them.`
- A voice rule, because repetition across weeks is the failure mode this block
  creates: `- Do not reuse an APPROVED POST's topic, opening line, example or
  phrasing. A post that repeats one of them has failed.`

**Tests** in `test/prompts.test.ts`. The existing `buildDraftingInput` calls all
gain the new argument; update them rather than adding a parallel describe block.
Then add:
- Block order: `<voice_samples>` < `<approved_posts>` < `<transcript>` < `<format>`,
  extending the existing order test.
- Each block carries its own content and not the other's — pass distinctly
  recognisable strings for samples and approved posts and assert each lands in
  its own block. Two adjacent `string[]` parameters cannot be told apart by the
  type checker, so this test is the only thing standing between a future
  refactor and a silent swap.
- Caps: at most `MAX_APPROVED_POSTS` survive, each sliced to `MAX_APPROVED_CHARS`
  (mirror the existing MAX_SAMPLES test).
- An empty `approvedPosts` still renders an empty block, in the right position.
- The two new instruction phrases are pinned alongside the existing ones.
- The compliance tests must still pass untouched: no imports in the source, and
  no meeting title or speaker label reachable through the payload.
  </action>
  <verify>
- `npm test` passes; the suite grows by roughly 5 tests and loses none
- `npm run check` exits 0
- `grep -c "^import" src/prompts.ts` returns 0
  </verify>
  <done>The prompt carries an approved-posts block in the cacheable prefix, the model is told what it may and may not take from it, and both are pinned by test.</done>
</task>

<task type="auto">
  <name>Task 2: Read the approved posts at the call site, and deploy the phase</name>
  <files>src/runs.tsx</files>
  <action>
In the drafting branch of the step route, beside the existing `listVoiceSamples`
read:

```
const approved = await listApprovedPosts(c.env.DB, MAX_APPROVED_POSTS, runId);
```

and pass it as the second argument to `buildDraftingInput`. Import
`MAX_APPROVED_POSTS` from `./prompts` and `listApprovedPosts` from `./db`: the
constant lives with the prompt, the query lives with the database, and the route
is the only place that knows both. This is the same shape as 03-06's coverage —
the caller computes, the helper stores — and it is what keeps `src/db.ts` free of
any prompt import.

Still primitives only at the call site: `approved` is a `string[]` of post
bodies, read out of the rows in `src/db.ts`, never a row array.

**Leave `checkGrounding` exactly as it is.** Its source pool stays
`[transcript.body, ...sampleBodies]`. Add a comment saying why approved posts are
absent, because the omission will look like an oversight to the next reader and
is not: approving a post for publication is not certifying that every claim in it
came from the executive's own material. Crediting it as grounding would let one
fabrication launder itself into a permanent source and be re-credited in every
run after — which is the same reason outlier bodies have never been in the pool.

One more D1 query in the step route, taking it from at most 10 to at most 11
against a Free-plan ceiling of 50 per invocation, and no extra subrequest.

Then deploy: `npm run deploy`, and record the version id in the summary.
  </action>
