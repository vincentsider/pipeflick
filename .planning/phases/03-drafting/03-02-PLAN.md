<task type="auto">
  <name>Task 2: Run and job helpers in src/db.ts</name>
  <files>src/db.ts</files>
  <action>
    Append a "Phase 3 runs (migration 0003)" section below the Phase 2 section. Bound
    parameters only; never interpolate. Export row types alongside the functions.

    - `createRun(db, transcriptId, outlierBodies: string[]): Promise<string>`
      Generates `crypto.randomUUID()`. Inserts the run, one `outliers` row per pasted body
      (position 1..N, status 'pending'), and exactly THREE `drafts` rows (position 1..3,
      status 'pending'). Assign `drafts.outlier_id` round-robin over the outliers by
      position, so two outliers give 1->A, 2->B, 3->A. DRAFT-02 requires three drafts each
      filled from one of the run's templates, not a bijection.
      Caller guarantees 2 or 3 bodies; assert it and throw otherwise.
      One statement per row (~7 queries) keeps well inside D1's 50-query Free-plan budget
      and its 100-bound-parameter cap.

    - `claimNextJob(db, runId): Promise<Job | null>` — the claim-then-work guard from
      03-RESEARCH.md Pattern 1, and the single most important function here.
      Order: every unfinished `outliers` row first (a draft cannot be written before its
      template exists), then `drafts` whose `outlier_id` has `template_json` non-null.
      Claimable means `status = 'pending'` OR (`status = 'running'` AND `started_at` older
      than 180s — crash recovery, comfortably past the 120s AbortSignal timeout).
      Claim with a conditional UPDATE and return null unless `meta.changes === 1`; a losing
      claim must change nothing. Increment `attempts` in the same UPDATE so a page reload
      cannot reset the loop counter.
      Return a discriminated union: `{ kind: "extract", id, outlierBody }` or
      `{ kind: "draft", id, template, outlierId }`.
      Do NOT use `RETURNING` — D1's support for it is undocumented (research Open Question 2).

    - `finishOutlier(db, id, template, usage)` / `finishDraft(db, id, post, sourceLines, grounded, usage)`
      Set status 'done', clear error columns, stamp `updated_at`. `finishDraft` writes
      `source_lines_json` and the grounded flag. Store the parsed values only, never the
      OpenAI response object.

    - `failJob(db, job, code, message)` — status 'failed', record `error_code` and
      `error_message`, stamp `updated_at`.

    - `getRunView(db, runId)` — ONE select per table (run, outliers, drafts), never N+1.
      Returns the run plus its jobs. The outlier projection must NOT include
      `template_json`: the status page has no use for it and omitting it at the query
      makes OUTL-02 structural rather than a rendering discipline. Do include enough to
      show progress: position, status, attempts, error_code, error_message.

    - `listRuns(db)` — id, transcript_id, transcript title via a join, status, created_at,
      and done/total counts. No draft or transcript bodies on a list page (the
      `TranscriptSummary` discipline from Phase 2).

    - `resetRunJobs(db, runId)` — set status 'pending', attempts 0, clear error columns and
      `started_at`, for every `outliers` and `drafts` row of the run WHERE status != 'done'.
      Completed jobs are untouched, so a retry never re-pays for a finished OpenAI call.
      Also set the run back to 'pending'.
  </action>
  <verify>

    insert a run with 2 outliers, confirm 3 draft rows exist with outlier_id round-robined

<task type="auto">
  <name>Task 3: OpenAI Responses client (src/openai.ts)</name>
  <files>src/openai.ts</files>
  <action>
    Implement `callStructured<T>` and `OpenAIError` following 03-RESEARCH.md "The Worker
    client (src/openai.ts)" closely — that code was written against the live API docs and
    the details are where this goes wrong from memory.

    Non-negotiables, each with its reason:
    - `text: { format: { type: "json_schema", name, strict: true, schema } }`. This is the
      Responses shape, FLATTENED compared to Chat Completions' `response_format`. Writing
      the Chat Completions shape is a guaranteed 400.
    - `store: false` on every request. The Responses API default is 30-day application-state
      retention, which is exactly the compliance question CLAUDE.md flags. Note in a comment
      that abuse-monitoring logs are still kept 30 days and that changing THAT needs a ZDR
      agreement — state it honestly rather than implying no retention at all.
    - Read the output with `body.output.find(i => i.type === "message")`. Reasoning models
      emit a `reasoning` item first, so `output[0]` is intermittently the wrong item.
    - Handle `content[0].type === "refusal"` as a non-retryable error carrying the model's
      own refusal text.
    - Handle `body.status === "incomplete"`: `incomplete_details.reason === "max_output_tokens"`
      is retryable-once, anything else is not. A truncated response is billed and returns
      nothing, so surface it distinctly.
    - `AbortSignal.timeout(opts.timeoutMs)`; on abort or network failure throw
      `OpenAIError("OpenAI did not respond in time", "timeout", 0, true)` and never echo
      the cause.
    - `res.body?.cancel()` when a non-2xx body will not be read.
    - Retryability branches on `error.code`, not status: 429 is both rate limiting AND
      billing exhaustion. `credit_balance_exhausted`, `organization_spend_limit_exceeded`,
      `project_spend_limit_exceeded` and `organization_usage_limit_exceeded` are NOT
      retryable — retrying them is an infinite loop that restores nothing.
    - Parse `Retry-After` into `retryAfterSeconds` when it is a plain integer.
    - Return `{ value, usage }` where usage carries `input_tokens`, `output_tokens` and
      `output_tokens_details.reasoning_tokens`.

    The key is an argument, exactly as in `src/fireflies.ts`. This module never reads
    `c.env`, never logs, and never puts the key, the request body or any transcript text
    into an error message. `OpenAIError.message` is always OpenAI's own text or one of a
    fixed set of strings, so it is always safe to render.

    Do not add the `openai` npm package. The project has one runtime dependency and
    `src/fireflies.ts` already sets the raw-`fetch` client pattern.
  </action>

  </verify>
