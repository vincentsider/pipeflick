<task type="auto">
  <name>Task 1: The /zernio connection page and account selection</name>
  <files>src/zernio-routes.tsx, src/db.ts</files>
  <action>
First, in `src/db.ts`, add two setting keys beside `SPEAKER_NAME_KEY`:
`export const ZERNIO_ACCOUNT_ID_KEY = "zernio.account_id"` and
`export const ZERNIO_ACCOUNT_LABEL_KEY = "zernio.account_label"`. Nothing else in `src/db.ts`
changes — `getSetting`/`setSetting` already do the work, as they do for the speaker name.

Create `src/zernio-routes.tsx` as `export const zernio = new Hono<AppEnv>()`, the feature-router
pattern from 02-02.

`GET /zernio`:
- No `ZERNIO_USER_TOKEN` → render an error page saying so and pointing at `/health`, status 500.
  Make **no request**. Copy the wording shape `src/fireflies-routes.tsx` uses for a missing
  `FIREFLIES_API_KEY`.
- Call `listLinkedInAccounts(c.env.ZERNIO_USER_TOKEN)`.
- `ZernioError` → render Zernio's own message plus its `code`, status 502. Never a stack. A 401
  gets an additional sentence of its own: the token is set but Zernio rejected it, so the value in
  `ZERNIO_USER_TOKEN` is not a valid Zernio API key — fix `.dev.vars` and run
  `npm run secrets:push`. That message is the difference between ten minutes and an afternoon, and
  DISCOVERY.md records that this is a genuinely likely state: the secret was named for Zernio at
  the 01-03 checkpoint, but what it holds has never been exercised.
- Success with **zero** accounts → not an error. A `.notice.warn` saying Zernio is connected but no
  LinkedIn account is connected inside Zernio, with the dashboard step named. This is the expected
  first-run state and must not render as a failure.
- Success with accounts → a `.notice` line naming the connection, then a form listing each account
  as a radio option (`displayName`, `username`, and whether `isActive`), with the currently stored
  `zernio.account_id` preselected. Submit posts to `/zernio`.

  An account whose `isActive` is false is still listed but shown as needing reconnection — do not
  hide it, or the page silently loses the account the user is looking for.

`POST /zernio`:
- Validate the submitted account id against the ids just listed rather than trusting the form. Use
  a pattern guard first (`/^[a-f0-9]{24}$/i` — Zernio ids are 24-char hex ObjectIds per the spec)
  and return a plain-text 400 before touching D1, matching the route-level validation style of
  02-02 and 04-02.
- Store the id under `ZERNIO_ACCOUNT_ID_KEY` and a human label (`displayName` or `username`) under
  `ZERNIO_ACCOUNT_LABEL_KEY`. The label is stored so the run page in 05-04 can say which account a
  push would go to **without spending a Zernio request on every page view** — the same instinct as
  03-06 storing the coverage counts rather than recomputing them at render.
- `303` redirect to `/zernio?saved=1` with a flash notice, the 02-02 pattern. No client JS.

Every route here reads `c.env.ZERNIO_USER_TOKEN` and passes it in. `src/zernio.ts` never reads the
environment; this file is the only place that knows the binding exists.
