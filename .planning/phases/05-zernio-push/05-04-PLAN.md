<task type="auto">
  <name>Task 1: The push route</name>
  <files>src/runs.tsx</files>
  <action>
Add `runs.post("/runs/:id/drafts/:draftId/push", ...)` directly after the decision route, mirroring
its structure so the two read as a pair.

Guards, in this order, each returning before anything is spent:
1. `RUN_ID_PATTERN` fails → `c.text("Invalid run id", 400)`.
2. `DRAFT_ID_PATTERN` fails → `c.text("Invalid draft id", 400)`.
3. No `c.env.ZERNIO_USER_TOKEN` → 500 pointing at `/health`, no request made.
4. No `zernio.account_id` in settings → `c.text(...)` 400 telling the user to choose an account on
   `/zernio`. This is a setup state, not a failure.
5. Load the draft via `getRunView` and find it by id; missing → 404. (`getRunView` is what 05-02
   widened, so the push columns arrive with it and cost nothing extra.)
6. `draft.decision` is not `"accepted"` or `"edited"` → 400. **This is the requirement, not a
   safety net.** SCHED-02 says an *accepted* draft; a rejected or undecided draft reaching Zernio
   would make the approval gate decorative, and CLAUDE.md calls that gate the product's trust
   mechanism.
7. `draft.final_body` is null or empty → 400. Push `final_body` and never `body`: `body` is the
   model's original output, which on a draft decided `edited` is text the executive explicitly
   changed and did not approve.
8. `draft.zernio_post_id` already set → 400 saying it is already in Zernio, with the id. One click,
   once. The route refuses even though Task 2 hides the button, because a stale open tab will
   happily re-post otherwise.
9. `final_body.length > MAX_LINKEDIN_CHARS` → 400 naming the limit and the actual length. Check it
   here rather than letting Zernio reject it: DISCOVERY.md records that `MAX_DECISION_BODY_CHARS`
   is 5000 and LinkedIn's ceiling is 3000, so a legally-stored draft can be too long, and a local
   check spends no request and gives a better message.

Then call `createLinkedInDraft(c.env.ZERNIO_USER_TOKEN, draft.final_body, accountId)`.

- Success → `recordPush(c.env.DB, runId, draftId, result.id)`, then `303` to `/runs/${runId}`.
- `ZernioError` with code `duplicate` → this is Zernio's 24-hour content-hash dedup telling us the
  post is already there and handing back `details.existingPostId`. **Record it with `recordPush`
  and redirect as a success.** The post exists in Zernio, which is what the user asked for; calling
  it an error would be a lie that also loses the id. Say so in a comment.
- Any other `ZernioError` → `recordPushFailure(c.env.DB, runId, draftId, error.code, error.message)`
  then `303` back, so the failure renders beside the draft rather than on an error page the user
  navigates away from. A `403` with code `ACCOUNT_DISCONNECTED` is the one worth special wording:
  the remedy is reconnecting in Zernio and re-choosing on `/zernio`, which the rendered message
  should say.
- A non-`ZernioError` throw (network, timeout) → `recordPushFailure` with a generic code and a
  message that does not include the exception text verbatim.

`recordPush` and `recordPushFailure` both return false when the draft belongs to another run;
turn false into a 404 exactly as the decision route does.

<task type="auto">
  <name>Task 2: The push control and the pushed-state panel</name>
  <files>src/runs.tsx</files>
  <action>
In `DraftSection`, below `DecisionRecord`, render the push state and control. Read the account
label from settings once per page render in the `GET /runs/:id` handler and pass it down as a prop
— not a Zernio request per page view, and not per draft.

States, in the order they are checked:
- `draft.zernio_post_id` set → a `.notice` reading "In Zernio as an unscheduled LinkedIn draft",
  the Zernio id, and the time from `zernio_pushed_at`. **No button.** Say plainly that it is
  unscheduled and unpublished: the executive must be able to tell at a glance that clicking this
  did not post anything to LinkedIn, because the whole product rests on that being true.
- `draft.zernio_error_code` set (and no post id) → amber `.notice.warn` with Zernio's message and
  code, then the push button again so a retry is one click. Amber, not red — 03-03's rule: red is a
  step that failed inside a run, and a push that Zernio declined is a thing to try again.
- Decision is `accepted` or `edited`, nothing pushed yet → the push form: a single button reading
  `Push to Zernio`, naming the account label ("as {label}") so the destination is never a guess.
  If no account is configured, render a hint linking to `/zernio` instead of a button.
- Decision is `rejected` or NULL → render nothing. A push control on an undecided draft invites
  exactly the mistake guard 6 in Task 1 exists to stop.

Gate the whole block on the existing `interactive` prop, for the reason 04-02 wrote down: the page
resubmits itself every 400ms while a run is generating, and a control that appears mid-reload is a
control that gets mis-clicked.

Update the explanatory paragraph in `RunControl` — it currently says "Nothing is published from
here". That is still true and now needs to say more: a push creates an **unscheduled draft** in
Zernio, and scheduling and publishing both stay manual, in Zernio. Do not weaken that sentence.

No new CSS. `.notice`, `.notice.warn` and `.hint` already carry every state here, as they did for
the decision record and the grounding panel.
  </action>
  <verify>
`npm run dev` with local D1 seeded so all five states exist at once in one run: pushed, failed,
pushable, rejected, undecided. Observe each rendering; confirm the pushed one has no button and the
failed one does. Confirm no push control renders while a run is auto-advancing. Then delete the
seed rows and confirm local D1 is back to zero.
  </verify>
  <done>All five states observed rendering correctly, and the auto-advance case observed hiding the control.</done>
