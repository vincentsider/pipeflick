<task type="auto">
  <name>Task 1: Zernio client with a draft-only request builder</name>
  <files>src/zernio.ts</files>
  <action>
Create `src/zernio.ts` following the shape of `src/fireflies.ts` exactly — same error-class
pattern, same "API key is an argument, never `c.env`" rule, same file-header comment explaining the
constraint the module exists to enforce.

Constants at the top, named, never inline at a call site (03-01's rule):
- `const ENDPOINT = "https://zernio.com/api/v1"` — base URL from DISCOVERY.md; paths append `/accounts`, `/posts`.
- `const TIMEOUT_MS = 20_000` — same as Fireflies, via `AbortSignal.timeout`.
- `export const MAX_LINKEDIN_CHARS = 3000` — LinkedIn's own ceiling, per the spec. Note in a
  comment that `MAX_DECISION_BODY_CHARS` in `src/runs.tsx` is deliberately 5000, so an accepted
  draft can legally sit in D1 at a length Zernio will reject; the caller checks before spending
  the request.
- `export const LINKEDIN_PLATFORM = "linkedin"`.

`export class ZernioError extends Error` carrying `code: string` and `status: number`, mirroring
`FirefliesError`. `code` is Zernio's own machine-readable `code` when it sends one
(`ACCOUNT_DISCONNECTED`, `ACCOUNT_NOT_ENABLED_FOR_POSTING`, `PROFILE_OVER_LIMIT`,
`PAYMENT_REQUIRED`), else `http_<status>`. Add a `details?: { existingPostId?: string }` field so a
409 can hand its `existingPostId` to the caller — see Task note below.

**`export function buildDraftRequest(content: string, accountId: string): Record<string, unknown>`**
— pure, no I/O, no fetch. Returns exactly:
  `{ content, isDraft: true, platforms: [{ platform: LINKEDIN_PLATFORM, accountId }] }`
and nothing else. Write the reason in a comment at the site: `isDraft: true` wins over
`publishNow` and `scheduledFor` per the spec's own precedence rule, and it is sent **explicitly**
rather than relying on the absence of those fields, because absence is a property a future
refactor can destroy silently while adding a feature. `platforms` is sent even though the spec
allows a draft to omit it — a draft with no target is not one click from being scheduled, which is
what SCHED-02 promises. This function exists as a separate export purely so Task 2 can pin it.

`export async function listLinkedInAccounts(token: string): Promise<ZernioAccount[]>` —
`GET /accounts?platform=linkedin&status=connected`. Map each to
`{ id: string; username: string; displayName: string; profileUrl: string; isActive: boolean }`
reading `_id` into `id`. Export the `ZernioAccount` type. This doubles as the connection check:
a bad token throws `ZernioError` with status 401.

`export async function createLinkedInDraft(token, content, accountId): Promise<ZernioDraft>` —
`POST /posts` with `buildDraftRequest(...)` as the body and a
`"x-request-id": crypto.randomUUID()` header (fresh per call — the spec warns that reusing one id
across logical calls makes every later call look like a retry of the first). Return
`{ id: string; status: string }` from `post._id` and `post.status`.

Handle the responses DISCOVERY.md lists:
- `200` — the `x-request-id` retry path, body carries `existingPost`. Read the id from
  `existingPost._id` and return it like a success; nothing was created and that is the correct
  outcome, not an error.
- `201` — success, read `post._id`.
- `409` — duplicate content within 24h. Throw `ZernioError` with code `duplicate` and
  `details.existingPostId` from `details.existingPostId`. The caller turns this into "already in
  Zernio" rather than a failure — pressing a button twice must not read as broken.
- Everything else — throw `ZernioError` with Zernio's `error` text and its `code` when present.

**Two things this file must never do**, both stated in comments:
1. Never read `c.env` or any environment. The token arrives as an argument. Routes are the only
   place that touches `c.env.ZERNIO_USER_TOKEN`.
2. Never put the token, the request body or the post text into an error message or a log.
   Additionally, run every Zernio-supplied message through a scrub for `sk_`-shaped fragments
   (`/sk_[A-Za-z0-9_*-]+/g`) before it leaves this module. Note in the comment that `scrubKey` in
   `src/runs.tsx` matches `sk-` (hyphen, OpenAI's shape) and Zernio's keys are `sk_` (underscore),
   so the existing helper does **not** cover this and the resemblance is a trap.

Do NOT use `dryRun` anywhere: the spec restricts it to TikTok, and a body with no `tiktok` entry is
rejected with 400. Do NOT add a `timezone` field: it only interprets a `scheduledFor` without an
offset, and this client never sends one.

<task type="auto">
  <name>Task 2: Pin the publish-safety property with a test</name>
  <files>test/zernio.test.ts</files>
  <action>
Create `test/zernio.test.ts` in the style of `test/prompts.test.ts` (vitest, `describe`/`it`/
`expect`, imports from `../src/...`).

Assert on `buildDraftRequest("some post text", "64e1f0a9e2b5af0012ab34cd")`:
- `isDraft` is exactly `true`.
- `publishNow`, `scheduledFor` and `queuedFromProfile` are **absent** — use
  `expect(body).not.toHaveProperty("publishNow")` and the same for the other two. `not.toHaveProperty`
  rather than `toBeUndefined()`: an explicitly-set `undefined` would pass the latter and would still
  serialise away, but the distinction matters if the shape is ever built by spreading a caller's
  object.
- `platforms` is a one-entry array whose entry is `{ platform: "linkedin", accountId: "64e1f0a9e2b5af0012ab34cd" }`.
- `content` is the text passed in, unmodified.
- The serialised body — `JSON.stringify(buildDraftRequest(...))` — does not contain the substrings
  `publishNow`, `scheduledFor` or `queuedFromProfile`. This is the assertion that survives a
  refactor which nests the fields somewhere unexpected.

Add a source-level assertion in the same style as `test/prompts.test.ts`'s zero-imports check: read
`src/zernio.ts` with `readFileSync` and assert the file contains no `publishNow: true` anywhere.

Write a comment at the top of the file stating plainly what it is for: this test is the only thing
between a plausible refactor and publishing to Vincent's real LinkedIn profile, which CLAUDE.md
puts out of scope in the strongest terms in the document. It is not a coverage test and should not
be deleted for being small.

Do not test the fetch paths. `src/fireflies.ts` and `src/openai.ts` have no tests for the same
reason — they are I/O, and the codebase's established line is that pure logic is pinned and network
calls are verified by driving the real thing. 05-04's checkpoint is where the network path gets
looked at.
