<task type="auto">
  <name>Task 1: Migration 0006 — push state on drafts</name>
  <files>migrations/0006_push.sql</files>
  <action>
Write `migrations/0006_push.sql` in the style of `0005_decisions.sql`: a header comment that
explains *why* each column exists and what NULL means, then one `ADD COLUMN` per `ALTER TABLE`
(D1/SQLite takes no more), none of them `NOT NULL` because rows already exist in both databases.

Columns:
- `zernio_post_id TEXT` — the `_id` Zernio returned. NULL means this draft has never reached Zernio.
- `zernio_pushed_at TEXT` — ISO timestamp of the last push attempt, success or failure.
- `zernio_error_code TEXT` — the `ZernioError.code` of the last failed attempt; NULL after a success.
- `zernio_error_message TEXT` — Zernio's own human-readable text; NULL after a success.

Write these facts into the header, because they are the ones a later reader will get wrong:
- **NULL `zernio_post_id` with a non-NULL `zernio_error_code` is a failed push**, and it is a real
  state, not a defect. Both halves are needed: SCHED-03 asks for the pushed state *and* a clear
  error on failure.
- **A successful push clears the error columns.** A draft that failed once and then succeeded is a
  pushed draft, and leaving stale error text beside a live post id would render as both at once.
- **Nothing here is ever published.** The Zernio post is a draft in Zernio; the id is a receipt for
  something sitting unscheduled in Vincent's Zernio account, not a LinkedIn URL. Published posts
  carry `platformPostUrl` and this project never creates one.
- The compliance note at the head of `0003_runs.sql` still governs. Nothing in this migration
  changes what leaves the Worker toward OpenAI.

Apply it to **local and remote** D1:
`npm run db:migrate:local` then `npm run db:migrate:remote`.

STATE records that `db:migrate:remote` has failed with Cloudflare API error 7403 ("account not
valid or not authorized") on a valid token twice in three remote migrations, then succeeded on an
immediate retry. If it happens, **retry once before re-authenticating** — it is a known transient,
not a credentials problem.
  </action>

new columns.

<task type="auto">
  <name>Task 2: Push writes and push state on the run read</name>
  <files>src/db.ts</files>
  <action>
Add to `src/db.ts`, following the conventions already in that file: bound parameters everywhere,
no `RETURNING` (undocumented in D1), and **no import from `src/prompts.ts` or `src/zernio.ts`** —
that file imports nothing from either and the boundary is load-bearing, so any constant a helper
needs is a caller-supplied primitive.

1. `export async function recordPush(db, runId, draftId, zernioPostId): Promise<boolean>` — one
   UPDATE setting `zernio_post_id`, `zernio_pushed_at` and `updated_at` to now, and **clearing
   `zernio_error_code` and `zernio_error_message` to NULL**. Scoped `WHERE id = ?n AND run_id = ?m`,
   returning `result.meta.changes === 1`. Ownership is the WHERE clause, exactly as `recordDecision`
   does it: no separate ownership SELECT, because that is a second round trip and a race.

2. `export async function recordPushFailure(db, runId, draftId, code, message): Promise<boolean>` —
   same shape, setting `zernio_error_code`, `zernio_error_message` and `zernio_pushed_at`, and
   **leaving `zernio_post_id` alone**. A draft that was pushed successfully and later failed a
   re-push still has its post in Zernio; blanking the id would lose the receipt for a post that
   exists. Cap `message` the way error text is capped elsewhere in this codebase — reuse the
   existing truncation constant for job error messages if there is one, otherwise add a named
   constant beside it and say what it is for.

3. Widen `DraftView` with `zernio_post_id: string | null`, `zernio_pushed_at: string | null`,
   `zernio_error_code: string | null`, `zernio_error_message: string | null`, and add the four
   columns to the `drafts` projection inside `getRunView`. Document on the type that a NULL
   `zernio_post_id` beside a non-NULL `zernio_error_code` is a failed push, so the page renders the
   error rather than nothing.

   **Do not add a second query.** The run page is at four reads and 04-01 worked to keep it there;
   these columns ride along in the projection that already runs.

4. Leave `listRuns` alone. The run list already carries per-draft decisions (04-01's flat-read
   grouped in JS) and the run list is not where SCHED-03 is satisfied — the run page is. Adding
   push state there is a second concern and a wider read for no requirement.

Comment each helper the way `recordDecision` and `listApprovedPosts` are commented: what it does,
and the one thing about it that is not obvious.
  </action>
