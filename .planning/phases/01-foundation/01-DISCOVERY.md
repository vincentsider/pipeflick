## Decisions

### 1. Framework: Hono 4.13 with `hono/jsx` server rendering

- Hono gives routing, middleware, typed bindings (`new Hono<{ Bindings: Env }>()`, D1 via `c.env.DB`) and server-side JSX with no build step beyond esbuild inside wrangler.
- JSX setup: tsconfig `"jsx": "react-jsx"`, `"jsxImportSource": "hono/jsx"`; page files are `.tsx`.
- Plain fetch handler rejected: Phases 2 to 5 add several pages and forms; hand-rolled routing would be rewritten by Phase 2.
- Types: `wrangler types` generates `worker-configuration.d.ts` (runtime + `Env` from wrangler.jsonc bindings and `.dev.vars`). No need for `@cloudflare/workers-types`. Generated file is gitignored and regenerated by `npm run check`.
- Scaffold by writing files directly rather than `npm create cloudflare` (C3 wants a fresh directory and its Hono template drags in extras). Reference versions on npm today: hono 4.13.7, wrangler 4.131.2, typescript 5.x.

### 2. Access gate: hostname-based Access application + `ctx.access` in the Worker

Cloudflare now exposes the authenticated Access identity to the Worker directly:

- `ExecutionContext.access?: CloudflareAccessContext` with `aud: string` and `getIdentity(): Promise<{ email, ... } | undefined>` (present in `@cloudflare/workers-types` 5.20260914.1 and generated by `wrangler types`).
- `ctx.access` is `undefined` when Access did not authenticate the request, so the Worker can **fail closed**: no Access context → 403. No JWT library, no team domain or AUD secrets to manage.
- Local dev: `wrangler.jsonc` `"access": { "dev": { "aud": "...", "identity": { "email": "..." } } }` simulates a signed-in user under `wrangler dev`. Remove the block to simulate unauthenticated.
- Caveat: Workers with a static `assets` binding run behind a router Worker that does **not** pass `ctx.access`. Phase 1 uses inline CSS and no assets binding; keep it that way.
- In Hono the execution context is `c.executionCtx` (throws if there is none; wrap in try/catch → 403).

Which Access application to create:

| Option | Destination | Notes |
|--------|-------------|-------|
| Hostname-based (chosen) | `type: self_hosted`, `domain: pipeflick.<sub>.workers.dev` | Docs explicitly allow a workers.dev hostname. Returns an `aud`. Protects only that hostname, so disable `preview_urls` to close the preview side door |
| Worker-level | `destinations: [{type: "worker", worker_id}]` | Needs the Worker's UUID (not the script name); dashboard button "Protect this Worker behind Access" does the same. Fallback if the API route fails |

Creating the app needs `POST /accounts/{account_id}/access/apps` with an API token holding **Access: Apps and Policies: Edit**. That token does not exist yet (dashboard-only to create) and Zero Trust must be enabled first (dashboard-only onboarding: team name, Free plan, card details requested but not charged). Both are `user_setup` items.

Policy: `decision: allow`, `include: [{ email: { email: "owner@example.com" } }, { email: { email: "owner.alt@example.com" } }]`. Login is by one-time PIN to those addresses; no identity provider setup needed.

Residual risk: the docs describe `ctx.access` next to hostname-based protection but do not state it word-for-word for that case. If, after login, the Worker still returns 403, fall back to verifying the `Cf-Access-Jwt-Assertion` header with `jose` (`createRemoteJWKSet(new URL("https://<team>.cloudflareaccess.com/cdn-cgi/access/certs"))`, `audience` = app `aud`, `issuer` = team domain). Plan 01-02 carries that recipe.

### 3. D1

- `wrangler d1 create pipeflick-db` → add `d1_databases: [{ binding: "DB", database_name, database_id }]` to wrangler.jsonc.
- Migrations live in `migrations/` (default), files `NNNN_name.sql`, applied with `wrangler d1 migrations apply pipeflick-db --local` (Miniflare SQLite under `.wrangler/state`, used by `wrangler dev`) or `--remote` (production). Applied migrations are recorded in the `d1_migrations` table.
- `wrangler d1 execute pipeflick-db --remote --command "..."` runs ad-hoc SQL against production; changes cannot be undone. Only use it for read-only checks in this phase.
- Phase 1 schema is deliberately minimal: a `settings` key/value table. Phase 2 needs it for the speaker name (VOICE-03) and the health page uses it for its write/read check. Transcript, sample, run and draft tables belong to their own phases.

### 4. Secrets

- `wrangler secret put KEY` (stdin), `wrangler secret bulk <file>` (.env or JSON format, up to 100 keys), `wrangler secret list` (names only). Each command deploys a new version.
- Local: `.dev.vars` in dotenv syntax, gitignored (`.dev.vars*`). `.dev.vars` takes precedence over `.env`.
- Names for this project: `OPENAI_API_KEY`, `FIREFLIES_API_KEY`, `METRICOOL_USER_TOKEN`. Metricool also needs a user id and blog id, but those are identifiers, not secrets; Phase 5 decides where they live.
- The health page reports set/not set per key by checking the value is a non-empty string. It never renders any part of the value.

### 5. Deploy

- `wrangler deploy` publishes to `https://pipeflick.<subdomain>.workers.dev`. If the account has no workers.dev subdomain registered, deploy fails with a message pointing at the dashboard; that is a one-time human step (Workers & Pages → workers.dev subdomain).
- `compatibility_date` must not be in the future: use `2026-09-01`. Add `nodejs_compat` flag now so later phases can use Node APIs if a client library needs them.
- `observability.enabled: true` so Worker logs are visible in the dashboard and `wrangler tail`.

## Not needed in Phase 1

- Test framework. Nothing in this phase is business logic; Phase 2 (speaker filtering) is the first TDD candidate and sets up vitest with `@cloudflare/vitest-pool-workers` then.
- R2, KV, Durable Objects, static assets binding.
- Custom domain. workers.dev is enough for a single-user pilot.
