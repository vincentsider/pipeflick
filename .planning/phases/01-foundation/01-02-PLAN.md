<task type="auto">
  <name>Task 1: Fail-closed Access middleware with local simulation</name>
  <files>src/access.ts, src/index.tsx, wrangler.jsonc</files>
  <action>
1. `src/access.ts`: export `requireAccess`, a Hono middleware (`createMiddleware` from `hono/factory`) typed with `Variables: { email: string }`.
   - Read the execution context inside try/catch: `const access = c.executionCtx.access` (`c.executionCtx` throws when there is no execution context; treat that as no access).
   - If `access` is undefined → `return c.text("Access required", 403)`. This is the fail-closed guarantee: if the Access application is removed or misrouted, the Worker still refuses. Do not add any bypass env var for production.
   - Otherwise `const identity = await access.getIdentity()`; `c.set("email", identity?.email ?? "unknown")`; `await next()`.
   - Also export a type `AppEnv = { Bindings: Env; Variables: { email: string } }` and switch `src/index.tsx` to `new Hono<AppEnv>()`.
2. `src/index.tsx`: `app.use("*", requireAccess)` registered before any route. Change the home page to show "Signed in as {c.get("email")}". No unauthenticated routes exist in this phase.
3. `wrangler.jsonc`: add `"access": { "dev": { "aud": "pipeflick-local", "identity": { "email": "owner@example.com" } } }`. This is a dev-only block; wrangler ignores it on deploy. `aud` is required whenever the block is present. With no block at all, `ctx.access` is undefined locally and every request gets 403, which is how to simulate an unauthenticated visitor.
4. `npm run check`. Confirm `worker-configuration.d.ts` declares `readonly access?: CloudflareAccessContext` on `ExecutionContext`; if the generated types lack it, upgrade wrangler and rerun before writing any workaround.
5. Local verification: start `wrangler dev`, `curl -s http://localhost:8787/` shows "Signed in as owner@example.com". Then run once more with the dev block temporarily removed (or `wrangler dev --config` pointing at a copy without it) and confirm 403 "Access required". Restore the block.
6. `npx wrangler deploy`. Because no Access application exists yet, `curl -s -o /dev/null -w "%{http_code}" https://pipeflick.<subdomain>.workers.dev/` must now print 403. This proves the gate closes on its own.
  </action>
  <verify>Local: 200 with the simulated email when the dev block is present, 403 without it. Remote: `curl -s -o /dev/null -w "%{http_code}" <url>` prints 403 after deploy. `npm run check` exits 0.</verify>
  <done>Worker refuses all requests without an Access context, locally and in production; local dev works via the simulated identity</done>
</task>

<task type="auto">
  <name>Task 2: Create the Access application for the workers.dev hostname</name>
  <files>scripts/create-access-app.sh</files>
  <action>
1. Write `scripts/create-access-app.sh` (bash, `set -euo pipefail`, executable). Inputs from the environment: `CF_ACCESS_API_TOKEN` (required), `ACCOUNT_ID` (default `YOUR_CLOUDFLARE_ACCOUNT_ID`), `HOST` (required, e.g. `pipeflick.<subdomain>.workers.dev`), `ALLOWED_EMAILS` (comma-separated, default `owner@example.com,owner.alt@example.com`). No values are hard-coded except the defaults above; nothing secret is written to disk.
   - Idempotency: `GET https://api.cloudflare.com/client/v4/accounts/$ACCOUNT_ID/access/apps`; if an app whose `domain` equals `$HOST` exists, print its `id` and `aud` and exit 0.
   - Otherwise `POST .../access/apps` with JSON:
     `{"type":"self_hosted","name":"Pipeflick","domain":"$HOST","self_hosted_domains":["$HOST"],"session_duration":"24h","app_launcher_visible":false,"policies":[{"name":"Vincent only","decision":"allow","include":[{"email":{"email":"<each allowed email>"}}]}]}`
     Build the include array from `ALLOWED_EMAILS` (one `{"email":{"email":...}}` object per address). Use `curl --fail-with-body` and print the `result.id` and `result.aud` from the response (jq if available, otherwise grep/sed).
   - On HTTP 403/401 or `access.api.error.not_enabled`, print the exact error and exit 1.
2. Run it: `HOST=<workers.dev hostname from 01-01-SUMMARY> scripts/create-access-app.sh`.
   - If `CF_ACCESS_API_TOKEN` is unset or the API says Access is not enabled, this is an authentication gate, not a failure: raise a `checkpoint:human-action` with the two `user_setup` steps (enable Zero Trust, create the token), then rerun.
   - Fallback if the API route cannot be made to work: the user can click Cloudflare dashboard → Workers & Pages → pipeflick → Access → "Protect this Worker behind Access" → All traffic → policy "Cloudflare account" → Apply Access. Record which route was used in the SUMMARY.
3. Verify the edge now gates the hostname: `curl -s -o /dev/null -w "%{http_code} %{redirect_url}\n" https://$HOST/` prints `302` and a `redirect_url` containing `cloudflareaccess.com`. A request with a forged header (`-H "Cf-Access-Jwt-Assertion: junk"`) gets the same 302.
4. Record the application `id`, `aud` and the team domain in the SUMMARY (these are identifiers, not secrets).
  </action>
  <verify>`curl -s -o /dev/null -w "%{http_code} %{redirect_url}" https://<host>/` shows 302 to a cloudflareaccess.com URL; rerunning the script prints the existing app instead of creating a second one</verify>
  <done>Hostname-based Access application exists with an allow policy for Vincent's emails; anonymous requests are redirected to the Access login</done>
</task>
